# Підключення Playbook через AGENTS.md

## Налаштуй інструкції проєкту

1. Використай прогалини, визначені перевіркою підключення поточного Skill. Прочитай чинний
   AGENTS.md і перевір фактичні шляхи й команди проєкту.
2. Створи AGENTS.md, якщо його немає, або доповни наявний. Збережи
   специфічні правила; суперечності погодь, не перезаписуй файл шаблоном.
3. Заповни блок підключення нижче фактичними абсолютними шляхами.
   Не залишай placeholders. Не змінюй інші репозиторії чи глобальні
   налаштування агента поза дозволеним scope.

```text
Engineering Playbook connection
Connection version: 1
Project root: <абсолютний корінь проєкту>
Playbook root: <абсолютний корінь Playbook>
Progress: <абсолютний шлях спільного progress проєкту>
Progress policy: читати перед роботою; оновлювати після кожної задачі/зміни для іншого чату; <Playbook root>/ai-rules/project-progress.md
Testing policy: нові тести лише за явним запитом; перед рішеннями про тести читати <Playbook root>/ai-rules/testing-policy.md
Git policy: commit/push виконує користувач
Approval policy: реалізація після погодження потрібного плану; суттєві відхилення погоджуються
Artifacts policy: внутрішні AI-артефакти локальні й у .gitignore; продуктова AI-функціональність цим правилом не обмежується
Scope policy: не вигадуй вимоги; уточнюй недостатню інформацію; погоджуй суттєві рішення й публічні контракти; пояснюй компроміси; надані дозволи не перепитуй
Access policy: дотримуйся дозволів на інструменти, файли й репозиторії; не зберігай секрети в repository
```

`Connection version` позначає формат блока. Перевір усі поля за
перевіркою підключення поточного Skill навіть за правильної версії.

Додай короткі проєктні інструкції, яких ще немає:

- призначення, погоджений scope й архітектурні межі;
- заборону записувати секрети в repository;
- українську мову design, plan і progress;
- точні посилання на чинні design/plan; якщо їх ще немає — зазнач це,
  не створюй їх під час налаштування AGENTS.md;
- перед роботою читати спільний progress і релевантні design/plan;
  після зміни порядку робіт оновлювати plan, після зміни задуму — design
  із потрібним погодженням; надані дозволи не перепитувати;
- фактичні команди перевірки та посилання на потрібні Skills і технічні
  правила. Перед рішеннями про тести застосовувати повну Testing Policy,
  включно з лімітом 20 сценаріїв і підрахунком параметризації.

Не вигадуй стан, approval, шляхи, команди чи недоступні пакети.
Перевір посилання з цільового проєкту; відносні шляхи з Playbook не копіюй
механічно. Короткі нагадування зв’яжи з повними джерелами. При зміні
постійних правил онови відповідні нагадування; поточні результати пиши
в progress, а не AGENTS.md.

Додай внутрішні AGENTS.md, design, plan і progress до .gitignore.
Уже відстежувані файли не видаляй із Git самовільно — повідом про розбіжність.

## Перехід наявного проєкту

Прочитай старі документи й зістав їх із фактичним станом. Перенеси:

- задум, цілі, концепцію, архітектурні рішення й напрямок розвитку — у design;
- етапи, порядок, залежності та невиконані задачі — у plan;
- поточний етап, виконане, рішення, відхилення, критичні деталі й наступну
  дію — у спільний progress зі збереженням прив’язок до планів.

Не називай старі наміри виконаними або погодженими без доказів.
Покажи відповідність старих розділів новим джерелам, перевір відсутність
втрат і онови посилання. Старі файли познач заміненими, не видаляй
автоматично. Не створюй окремі roadmap/runtime; зв’язки між планами
записуй у планах. Уже погоджені рішення не проводь через Brainstorm
повторно лише через перенесення документів.

## Розташування Playbook і пошук документів

Збережи в локальному AGENTS.md абсолютні `Project root`, `Playbook root`
і `Progress`. Використай корені запуску; за відсутності Playbook root
визнач його з фактичного розташування цього файла:
`<Playbook root>/ai-rules/project-agent-instructions.md`.
Не вгадуй локальний шлях за GitHub name і не записуй шлях машини як
універсальну константу у спільні інструкції або Skills.

Запиши правило пошуку документів:

- початковий шлях `skills/.../SKILL.md` рахувати від Playbook root;
- відносний Markdown-link рахувати від папки файла, що містить посилання,
  а не від робочого каталогу shell; зберігати розташування прочитаного файла;
- `engineering-playbook:назва` використовувати як назву Skill, а файлове
  посилання поруч — як шлях до його інструкції;
- потрібні файли читати самостійно дозволеним інструментом у поточному
  thread, без запиту на пересилання кожного reference;
- при відсутньому корені/файлі або браку доступу повідомляти конкретну
  проблему; не шукати заміну в чужих репозиторіях чи старих plugin caches;
- у відновленій сесії використовувати ті самі явно визначені корені.

## Перевір і заверши

Повтори перевірку підключення, з якої поточний Skill направив тебе сюди.
Перевір доступність збережених шляхів і посилань. Перечитай змінений
AGENTS.md і перевір, що записані значення відповідають фактичному
підключенню.

Запиши виконані зміни й результат перевірки у спільний progress проєкту.
За успішного checkpoint повернися до поточного Skill. Якщо налаштування
заблоковане, назви прогалину й не позначай його завершеним.

# Project Conventions
Цей документ описує інженерні принципи, яких я дотримуюся незалежно від конкретної архітектури.
Вони є інваріантами моїх проєктів і застосовуються однаково до:

- Modular Monolith
- Simplified Hexagonal Architecture
- Hexagonal Pipeline
- Event-driven 

Архітектурні особливості конкретного стилю описуються окремо в папці `architectures/`.


# 0. Shared Technical Services

## Rule
Технічні механізми, які використовуються багатьма компонентами, повинні мати єдину точку реалізації.

Приклади:

- генерація ID;
- отримання поточного часу;
- серіалізація;
- хешування;
- генерація випадкових значень.

Бізнес-код не повинен знати, як саме реалізовані ці механізми.

---

# 1. Explicit over Magic

## Rule
Перевага завжди надається явній поведінці системи.

## Why
Код повинен бути максимально передбачуваним.
Явні рішення простіше:

- читати;
- дебажити;
- оптимізувати;
- підтримувати;
- аналізувати AI.

При конфлікті між "красивою магією" та явною реалізацією перевага віддається явній реалізації.

---

## Суть правила не в тому, що "контролер робить мапінг", а в тому, що мапінг відбувається на межі між зовнішнім контрактом і внутрішньою моделлю.
Для REST це контролер.
Для Telegram-бота — Telegram Adapter.
Для Kafka — Kafka Listener.
Для CLI — Command Handler.
# 2. Domain First

## Rule
Якщо існуюча Domain Model повністю описує бізнес-сутність або сценарій, вона використовується повторно.
Нові DTO або проміжні моделі створюються лише тоді, коли вони:

- додають нову відповідальність;
- відокремлюють зовнішній контракт від внутрішнього домену;
- адаптують Domain Model до вимог зовнішнього контракту.

Request/Response DTO належать виключно до зовнішнього контракту системи.
Мапінг між DTO та Domain Model виконується на межі системи — як правило, у Controller або іншому Adapter.
Після мапінгу, якщо Domain Model повністю описує бізнес-задачу, саме вона передається далі в Application Layer.
Також DTO створюється якщо треба мутувати domain модель для зовнішнього контракту.

## Why
Кожна нова модель збільшує складність системи.
Повторне використання Domain Model зменшує кількість маперів, дублювання коду та когнітивне навантаження.
Розміщення мапінгу на межі системи ізолює зовнішній контракт від внутрішньої моделі.
Це не забороняє use-case сервісу приймати чи повертати власний стабільний
API DTO: `api/internal/dto` або спільний `api/dto` є контрактом capability.
Якщо HTTP та internal мають однакову семантику й форму, спільний DTO
можна використати без дублюючого mapper. HTTP-specific envelopes та
provider DTO не стають через це моделями domain. Domain не залежить від
API-пакетів; API відображає потрібний результат domain.

# 3. Framework Isolation

## Rule
Бізнес-модель не повинна залежати від конкретного фреймворку.
Framework є деталлю реалізації.

## Приклади
Domain не залежить від:

- Spring
- JPA
- Jackson
- Lombok
- HTTP
- PostgreSQL

---

# 4. Package Responsibilities

## Rule
Кожен пакет має одну чітку відповідальність.
Пакети не повинні дублювати ролі один одного.

Приклади:

- bootstrap — запуск застосунку
- infrastructure — конфігурація
- application — orchestration
- adapter — інтеграція із зовнішнім світом
- domain — бізнес-модель

Для feature-oriented модулів вхідні контракти зібрані в `<feature>/api`:
`internal` — Java API між модулями; `web` — controllers, requests,
responses/responds, DTO, exceptions і mappers HTTP-межі; `api/dto` —
спільні контрактні моделі internal і web цього власника.
Internal-only моделі залишаються в `api/internal/dto`, web-only — в
`api/web`. Спільний DTO не є domain/entity чи DTO зовнішнього provider.
Створюй тільки потрібні пакети, дотримуйся naming проєкту.

Сервіс можна декомпозувати на цілісні use-case підсервіси, залишивши
головному сервісу координацію. Це не вимога розділяти кожен метод або
створювати interface для кожного класу. Повне дерево, ownership DTO,
exceptions і відповідність реальним проєктам:
[Структура одного модуля](../architectures/modular-monolith.md#структура-одного-модуля).

Конкретна внутрішня структура пакетів визначається архітектурою.

# 5. Configuration Driven

## Rule
Поведінка системи повинна визначатися конфігурацією, а не зміною коду.

Приклади:

- batch size
- retry
- executor
- providers
- enabled steps
- export mode

2# 6. Group by Business Responsibility

## Rule
Код групується за бізнес-відповідальністю, а не за технічним типом.

Добре:
article/
image/
video/
author/

Погано:

Організовувати весь проєкт лише за технічними типами:

controllers/
repositories/
services/

Конкретна структура проєкту визначається вибраною архітектурою.

# 7. Single Responsibility

## Rule
Кожен компонент повинен відповідати за одну чітко визначену область відповідальності.
Компонент може містити декілька методів, якщо всі вони логічно реалізують одну й ту саму відповідальність.
Не потрібно розділяти компонент на декілька класів лише тому, що він має декілька методів або операцій.
Розділення виконується лише тоді, коли нова відповідальність не належить до поточної області компонента.

## Examples

Добре:

ArticlePersistenceService
- save()
- update()
- delete()
- find()

Усі методи реалізують одну відповідальність — роботу зі сховищем Article.

Погано:

ArticleService
- downloadHtml()
- parseHtml()
- saveArticle()
- exportJson()
- sendEmail()

Компонент поєднує декілька незалежних відповідальностей, які повинні бути розділені.

## Why
Single Responsibility не означає створення максимальної кількості дрібних класів.
Мета принципу — зробити компоненти цілісними та зрозумілими.
Якщо декілька методів реалізують одну відповідальність і природно працюють разом, вони повинні залишатися в одному компоненті.
Розділення повинно спрощувати систему, а не збільшувати кількість класів без практичної користі.

---

# 8. Single Source of Truth

## Rule
Кожна бізнес-логіка повинна мати одне місце реалізації.
Не допускається дублювання однакової логіки в різних компонентах.
Якщо декілька компонентів потребують однакової поведінки, вона повинна бути винесена в окремий компонент або сервіс.

## Examples

Добре:
PriceCalculator
↓
використовується в OrderService, InvoiceService та CheckoutService.

Погано:
OrderService має власний розрахунок ціни.
InvoiceService має інший, але майже ідентичний розрахунок.
CheckoutService має ще одну копію тієї ж логіки.

## Why
Дублювання бізнес-логіки призводить до:

- різної поведінки системи;
- складнішої підтримки;
- необхідності виправляти одну й ту саму помилку в декількох місцях.

Кожна бізнес-логіка повинна мати єдине джерело істини (Single Source of Truth).

---

# 9. Simplicity over Generalization

## Rule
Спочатку вирішується поточна задача максимально простим способом.
Універсальні рішення, абстракції та framework-и створюються лише тоді, коли вони вирішують реальну проблему, а не потенційну майбутню потребу.
YAGNI (You Aren't Gonna Need It) має пріоритет.

## Why
Передчасні абстракції:

- збільшують складність;
- ускладнюють підтримку;
- часто не використовуються;
- роблять код менш зрозумілим.

Система повинна розвиватися разом із реальними вимогами, а не з припущеннями про майбутнє.

---

# 10. Design for Evolution

## Rule
Не реалізовувати функціональність наперед.
Але архітектура повинна залишатися відкритою для тих змін, які є природним розвитком системи.
Якщо майбутнє розширення очевидне і його підтримка майже не ускладнює поточну реалізацію, допустимо закласти відповідні точки розширення.

## Examples

Добре:

- Port для сховища.
- Executor, який поки працює з одним потоком.
- Batch API, навіть якщо зараз batch size = 1.

Погано:

- Framework на 20 інтерфейсів для задачі, яка поки має одну реалізацію.
- Абстракції, які не вирішують жодної поточної проблеми.

## Why
Архітектура повинна бути простою сьогодні, але не заважати розвитку завтра.
Мета полягає не у передбаченні всіх можливих змін, а у тому, щоб зробити найбільш очевидні напрямки розвитку дешевими для реалізації.

# 11. Readable Code

## Rule
Код повинен бути максимально зрозумілим як людині, так і AI.
Основна мета — щоб призначення класу, методу або змінної було зрозумілим без необхідності читати його реалізацію.

Для цього використовуються:

- прості та зрозумілі назви;
- послідовний неймінг;
- однакові патерни реалізації;
- єдина структура пакетів;
- мінімум прихованої логіки;
- явні залежності.

Перевага завжди надається простим і загальновідомим англійським словам.
Не використовувати рідкісні або складні слова лише заради "красивого" неймінгу.
Назва повинна одразу пояснювати призначення компонента.


Код пишеться на рівні senior розробника з повагою до читача та колег.
Складну логіку розбивати на зрозумілі методи з чіткою відповідальністю,
без зайвого дроблення та абстракцій. Орієнтуватися на приклади цього
Playbook і погоджений стиль проєкту.

У production Java-коді типи вказуються явно: `var` не використовувати.
`var` дозволений лише в тестах, створених за правилами
[Testing Policy](general.md#testing-policy).

## Agreed Java Code Style

Цей стиль обов'язковий для всіх проєктів: застосовуй його одразу до нового
коду та змінюваних фрагментів. Орієнтир — погоджений readability refactor
`features/projects/main/services/ProjectService.java` та погоджені
security/users класи. Нижче зафіксовано самі правила, тому читання цих
проєктних файлів не є обов'язковою залежністю для інших проєктів.

Старі сторонні класи проєктів масово не форматуй без доручення.
Наявні приклади Playbook залишаються актуальними: кожен показує рішення
для своєї ситуації. Нові правила уточнюють оформлення, а не скасовують
попередні приклади, їхні фабрики, інваріанти чи архітектурні підходи.
Підтримуй оформлення прикладів узгодженим, зберігаючи їхній зміст.
Вибирай доречний приклад за контекстом задачі; не нав'язуй один шаблон
усім ситуаціям і не перенось бізнес-рішення механічно.

### Enum and Record

- Enum: відступ 4 пробіли, кожна константа на окремому рядку.
  Порожній рядок після `{` та між константами.
- Record: `(` одразу після назви, потім порожній рядок. Кожен компонент
  окремим рядком із відступом 8 пробілів; між компонентами порожній рядок.
  Закривна `)` на окремому рядку. Анотацію залишай на рядку компонента,
  якщо він читабельний і вкладається в межу рядка; інакше перенось анотацію.
  Правило діє для DTO, entities, search records і вкладених records.

```java
public enum ProjectStatus {

    ACTIVE,

    DISABLED
}
```

```java
public record ProjectRequest(

        @NotBlank String name,

        @Nullable String notes
) {
}
```

### Class Structure and Logical Steps

- Порядок: константи → final залежності → public методи сценаріїв →
  private допоміжні методи.
- Public метод показує послідовний сценарій; private метод — цілісний
  названий крок. Не створюй helper для кожного рядка.
- Порожніми рядками відділяй отримання даних, перевірки/early return,
  побудову об'єкта, запис і формування результату. Не зливай метод у
  суцільний блок і не відділяй механічно кожен рядок.
- Замість вкладених обчислень в аргументах вводь змістовні локальні змінні:
  `total`, `activeCount`, `inactiveCount`, `draftCount`. Не створюй
  проміжні змінні, які не допомагають читанню.
- Повторні immutable значення винось в іменовану константу на кшталт
  `EMPTY_COUNTS` за реального повторення. Не створюй константу для
  кожного літерала або одноразового об'єкта.
- `toRespond()` послідовно відображає поля. Цілісну логіку, наприклад
  `availableActions()`, тримай в окремому private методі. Не створюй
  mapper/service класи лише заради скорочення поточного класу.
  Це правило оформлення не переносить HTTP-мапінг через архітектурні межі.

### Line Breaks, Builders and Arguments

Орієнтуйся на налаштовану праву межу рядка (right margin) IntelliJ IDEA
у конкретному проєкті. Не вигадуй універсальний ліміт символів.
Короткий зрозумілий виклик, сигнатура, `return` або `throw` лишається
в одному рядку, якщо вкладається в цю межу, крім явних правил нижче.

- Builder завжди багаторядковий, навіть якщо вміщається: початковий
  вираз окремо, кожен `.field(...)`/`.set(...)` з нового рядка,
  `.build()` також окремо.
- Створення DTO, зокрема `new XxxRespond(...)`, завжди оформлюй
  багаторядково: один аргумент на рядок, закривна дужка окремо,
  навіть якщо весь виклик вміщається в один рядок.
- У ланцюжку `.orElse(...)` та `.orElseThrow(...)` починай з нового рядка
  перед крапкою, як у погодженому `ProjectService`. Коротку lambda з
  `new Exception(...)` залишай на цьому рядку, якщо вона вміщається.
- Довгі stream, Criteria, Query та options chains рознось за кроками:
  кожен перенесений виклик починається з крапки на новому рядку.
  Вкладені `orOperator`/`andOperator` оформлюй з окремим рядком на кожну
  умову та відповідним відступом.
- Довгі сигнатури, звичайні виклики й конструктори рознось по одному
  параметру/аргументу на рядок, закривну дужку — окремо. Особливо
  уважно оформлюй Mongo-виклики. Короткі виклики без зазначених вище
  винятків не розтягуй механічно.
- Простий тернарний вираз, як у `statusOf()`, лишай в один рядок.
  Довгі гілки перенось; вкладені тернарні вирази не використовуй.

```java
ProjectSearch search = ProjectSearch.builder()
        .ownerUserId(currentUser.id())
        .text(text)
        .build();

ProjectEntity project = projectDao.findProjectById(projectId)
        .orElseThrow(() -> new ProjectNotFoundException(projectId));

return new ProjectRespond(
        project.id(),
        project.name(),
        availableActions(project, currentUser)
);
```

### Readability Refactor Boundaries

Зберігай бізнес-правила, порядок операцій, `null`/`false` semantics,
Mongo guards та API-контракти. Не додавай нові actions, поля чи абстракції
«для зручності». Якщо виявлено непогоджену архітектурну або продуктову
неоднозначність — спочатку постав питання; не вирішуй її форматуванням.

## Examples
Якщо для розуміння призначення компонента потрібно відкривати його реалізацію, швидше за все, назва вибрана невдало.

Добре:

- ImageDownloader
- JsonExporter
- ArticleParser
- VideoService
- RetryPolicy

Гірше:

- ArtifactResolver
- EntityAssembler
- PayloadCoordinator

якщо простіші назви точніше описують їхню відповідальність.

## Why

Читабельний код:

- швидше розуміється;
- простіше підтримується;
- зменшує кількість помилок;
- краще аналізується AI;
- скорочує час на входження в проєкт.

# 12. Consistency

## Rule
У межах одного проєкту однакові задачі повинні вирішуватися однаковим способом.
Не змішувати різні стилі, патерни чи підходи без обґрунтованої причини.
Перевага завжди надається консистентності проєкту, а не особистим вподобанням.

## Examples

Добре:

- Усі REST API використовують однакову структуру Controller → Mapper → Service.
- Усі винятки обробляються одним способом.
- Усі репозиторії мають однакову структуру.
- Усі DTO називаються за однаковими правилами.

Погано:

- В одному модулі використовується Constructor Injection, а в іншому — Field Injection.
- Частина сервісів повертає Optional, інша — null.
- В одному місці використовується UUID, в іншому — Long без очевидної причини.

## Why

Консистентний проєкт:

- легше читати;
- легше підтримувати;
- швидше розширювати;
- простіше аналізувати AI;
- зменшує кількість випадкових помилок.

Новий код повинен виглядати так, ніби його написала одна людина.

---

# 13. Observable Processing

## Rule
Будь-який довготривалий процес, pipeline або batch-операція повинні залишати достатньо інформації для подальшої діагностики без повторного запуску.
Мінімальний набір інформації:

- статус виконання;
- причина помилки (якщо є);
- контекст, необхідний для повторної обробки;
- можливість відфільтрувати невдалі результати.

## Why

Після завершення роботи системи повинно бути можливо відповісти на питання:

- Що було успішно оброблено?
- Що не вдалося?
- Чому саме?
- Чи можна повторити лише невдалі елементи?
- Які помилки зустрічаються найчастіше?

Без цієї інформації будь-який pipeline перетворюється на "black box", який складно підтримувати та аналізувати.

## Examples

Типові приклади:

- status
- errorMessage
- processedAt
- retryCount
- processingTime

Конкретна реалізація (Result-об'єкти, статусні таблиці, журнали виконання, event-и тощо) визначається архітектурою конкретного проєкту.

---

# 14. Automatic Technical Metadata

## Rule

Технічні метадані повинні заповнюватися автоматично тим компонентом, який за них відповідає.

До таких метаданих належать:

- createdAt
- updatedAt
- version
- createdBy
- modifiedBy

Бізнес-логіка не повинна вручну встановлювати ці значення.

## Why

Автоматичне керування технічними метаданими:

- усуває дублювання коду;
- зменшує кількість помилок;
- гарантує консистентність даних;
- дозволяє бізнес-коду концентруватися лише на бізнес-логіці.

## Examples

У Spring Boot + Hibernate:

- `@CreationTimestamp`
- `@UpdateTimestamp`

Mapper-и не повинні встановлювати ці поля вручну.

# 15. Store Time as Instant

## Rule
Абсолютний час повинен зберігатися та передаватися як `Instant`.
Часові пояси використовуються лише на межі системи — під час відображення інформації користувачу або інтеграції із зовнішніми системами.
Бізнес-логіка не повинна залежати від локальної часової зони сервера.

## Why

Часові пояси є однією з найпоширеніших причин помилок у розподілених системах.
Використання `Instant` забезпечує:

- єдине представлення часу;
- незалежність від часової зони сервера;
- коректну роботу між різними країнами та дата-центрами;
- просте порівняння часових міток.

## Examples

Добре:

- `Instant`
- `Clock.systemUTC()`

Уникати використання:

- `LocalDateTime.now()`
- `new Date()`

для зберігання абсолютного часу.

Часові пояси (`ZoneId`) повинні застосовуватися лише під час форматування або взаємодії із зовнішніми системами.

# 16. Prefer JSON for Embedded Data

## Rule
Якщо дані не є самостійною бізнес-сутністю і існують лише як частина одного агрегату, допускається використання їх у JSON-полі замість створення окремих таблиць.
До таких даних можуть належати:

- історія змін;
- версії документа;
- списки тегів;
- службові метадані;
- конфігурації;
- результати обробки.

Окремі таблиці створюються лише тоді, коли дані мають власний життєвий цикл, бізнес-логіку або повинні незалежно запитуватися, фільтруватися чи зв'язуватися з іншими сутностями.

## Why

JSON дозволяє:

- зменшити кількість таблиць;
- уникнути зайвих JOIN;
- спростити модель даних;
- зберігати вкладені структури природним способом.

Реляційна модель повинна використовуватися для бізнес-зв'язків, а не для кожної вкладеної структури.

# 17. Rule Hierarchy

## Rule
Project Conventions визначають загальні інженерні принципи, які застосовуються до всіх проєктів.
Конкретна структура проєкту, розташування пакетів і взаємодія компонентів визначаються вибраною архітектурою.
Перед внесенням змін необхідно застосовувати правила в такому порядку:

1. Визначити архітектуру проєкту.
2. Застосувати правила цієї архітектури.
3. Поверх них застосувати Project Conventions.

Якщо правила різних рівнів суперечать одне одному, пріоритет має більш спеціалізований рівень.

## Examples
Project Rules
↑
Architecture
↑
Project Conventions

## Why

Project Conventions відповідають на питання:

- як писати код;
- як організовувати відповідальності;
- яких принципів дотримуватися.

Архітектура відповідає на питання:

- де розташовуються компоненти;
- як вони взаємодіють;
- які пакети існують;
- як організовані залежності.

Обидва рівні доповнюють один одного і не суперечать один одному.

# 18. Named Static Factory Methods for Records

## Rule

Якщо `record` представляє декілька семантично різних результатів або
валідних станів, для його створення використовуються іменовані статичні
фабричні методи.

Назва фабрики повинна описувати стан або намір створення, наприклад:

- `accepted(messageId)`;
- `rejected(error)`;
- `unknown(error)`;
- `success(value)`;
- `failure(error)`.

Код, який використовує такий `record`, повинен викликати готову фабрику,
а не вручну повторювати комбінацію enum-значень, `null` та інших
службових аргументів у canonical constructor.

Compact constructor залишається єдиним місцем перевірки інваріантів,
щоб некоректний стан не можна було створити ані через фабрику, ані через
прямий виклик canonical constructor.

Це правило застосовується, коли фабрика:

- робить намір виклику очевидним;
- представляє дозволений стан об'єкта;
- приховує технічні аргументи або допустимі `null`-комбінації;
- не дублює бізнес-логіку, що належить іншому компоненту.

Для простого `record`, у якого є лише один очевидний спосіб створення і
всі аргументи однаково потрібні, додавати фабрику без практичної користі
не потрібно.

## Example

```java
import java.util.Objects;

public record SendMessageResult(

        SendOutcome outcome,

        String messageId,

        SendError error
) {

    public SendMessageResult {
        Objects.requireNonNull(outcome, "outcome must not be null");

        if (outcome == SendOutcome.ACCEPTED && error != null) {
            throw new IllegalArgumentException(
                    "Accepted send result must not contain an error"
            );
        }

        if (outcome != SendOutcome.ACCEPTED && error == null) {
            throw new IllegalArgumentException(
                    "Rejected or unknown send result must contain an error"
            );
        }
    }

    public static SendMessageResult accepted(String messageId) {
        return new SendMessageResult(
                SendOutcome.ACCEPTED,
                messageId,
                null
        );
    }

    public static SendMessageResult rejected(SendError error) {
        return new SendMessageResult(
                SendOutcome.REJECTED,
                null,
                error
        );
    }

    public static SendMessageResult unknown(SendError error) {
        return new SendMessageResult(
                SendOutcome.UNKNOWN,
                null,
                error
        );
    }
}
```

Використання:

```java
return SendMessageResult.accepted(messageId);
return SendMessageResult.rejected(error);
```

Уникати:

```java
return new SendMessageResult(
        SendOutcome.ACCEPTED,
        messageId,
        null
);
return new SendMessageResult(
        SendOutcome.REJECTED,
        null,
        error
);
```

## Why

Іменовані статичні фабрики:

- роблять виклик самодокументованим;
- централізують правильні комбінації полів;
- зменшують ризик переплутати аргументи або створити невалідний стан;
- спрощують зміну внутрішньої структури `record`;
- забезпечують однаковий стиль створення result/value objects у всьому
  проєкті.

# 19. Consistent Error Handling

## Rule

REST API та Security handlers використовують єдиний формат помилки зі
стабільним `code` і безпечним повідомленням. HTTP-мапінг залишається на
web-межі; бізнес-винятки належать своїм модулям і не залежать від HTTP.
Неочікувані збої логуються, внутрішні деталі не передаються клієнту.

Структура, правила та reference implementation:
[Error Handling](error-handling.md).

# 20. Web API Contracts

## Rule

Для сутностей із вибором дій backend повертає `availableActions` з
урахуванням прав і стану. Endpoint операції повторно перевіряє ці умови.
Для пагінованих HTTP-списків використовуй Spring Data `PagedModel<T>`
зі сторінкою DTO; пагінація та обмеження доступу виконуються в базі даних.

Правила, межі застосування та приклади:
[Web API Contracts](web-api.md).

# 21. Isolated Dev and Prod Environments

## Rule

Prod та dev мають окремі Docker Compose projects, backend/DB services,
networks, volumes, env-файли, credentials і порти. Спочатку формується
prod, потім dev за тією самою структурою; існуючі production data та
resource names зберігаються до явної міграції.

Структура, повні приклади та порядок реалізації:
[Dev and Prod Environments](environments.md).

# Спільні правила реалізації

## Before Implementation

Перед реалізацією будь-якої задачі:

1. Досліди поточну структуру проєкту.
2. Визнач існуючу архітектуру.
3. Знайди схожі реалізації.
4. Проаналізуй компоненти, які будуть зачеплені.
5. Дотримуйся поточної архітектури проєкту.
6. Не порушуй існуючі архітектурні принципи.
7. Перевір актуальні design, plan та progress файли, якщо вони існують,
   щоб зрозуміти загальну концепцію, поточний етап і вже прийняті
   рішення.

## Implementation

Під час реалізації:

- Роби мінімально необхідні зміни.
- Не змінюй код, який не відноситься до задачі.
- Не роби рефакторинг без окремої необхідності.
- Не додавай нові абстракції без реальної причини.
- Дотримуйся існуючого naming та package structure.
- Використовуй існуючі підходи проєкту, якщо вони не порушують
  архітектуру.
- Після кожної задачі або окремої зміни онови спільний progress проєкту
  перед наступною роботою за [правилами журналу (project-progress.md)](../../../ai-rules/project-progress.md),
  пиши для іншого чату без доступу до цієї розмови. Якщо зміни впливають на
  загальний план --- також plan.

## Unexpected Situations

Спочатку визнач вплив проблеми на погоджений результат.

Власні помилки реалізації й дрібні технічні рішення виправляй самостійно,
якщо вони не змінюють вимоги, погоджену поведінку, архітектуру,
публічні контракти, scope, загальний порядок або залежності плану й дозволи.
Наприклад, можеш інакше організувати приватний метод або вибрати
еквівалентний локальний алгоритм у межах погоджених обмежень.
Не запитуй дозволу на кожну таку зміну. Перевір результат і запиши
нетривіальний вибір як Ruling: рішення — причина — наслідок помилки.

Якщо проблема потребує нового scope, зміни погодженого рішення чи
загального плану, бракує дозволу або суттєвих даних для вибору:

1. Зупини зачеплену реалізацію та залежні задачі.
2. Опиши проблему, її вплив і можливі варіанти з плюсами та мінусами.
3. Використай уже надане рішення/дозвіл; якщо його немає, дочекайся
   рішення користувача через канал поточної сесії або координатора.
4. Онови plan / progress; якщо змінився задум або очікувана поведінка —
   також design чи відповідне джерело вимог.
5. Після потрібного погодження продовжуй зачеплену роботу.

Незалежну дозволену роботу можеш продовжувати, якщо вона не спирається
на невирішене питання. Новий баг поза scope запиши й поверни користувачу;
не виправляй його автоматично. Розмір diff не визначає суттєвість рішення:
навіть однорядкова зміна контракту може потребувати погодження.

## Code Reuse

Перед створенням нової реалізації виконай такі дії:

1. Перевір, чи вже існує аналогічна логіка в проєкті.
2. Оціни можливість повторного використання існуючої реалізації.
3. Якщо логіка значною мірою дублюється, запропонуй винесення
   спільної частини в абстракцію (інтерфейс, базовий клас, спільний
   сервіс або інший механізм, що відповідає поточній архітектурі).
4. Не дублюй код, якщо його можна перевикористати без порушення
   архітектурних принципів.
5. Якщо пропонуєш нову абстракцію, поясни, чому вона потрібна та
   яку проблему вирішує.

## Спільні технічні правила

Застосовуй локальні інструкції й технічні правила погодженого стека.

- Перед змінами коду прочитай релевантні загальні принципи
  [project-conventions.md](../../project-init/references/project-conventions.md#11-readable-code).
  Java style застосовуй лише до Java; не перенось мовні чи framework-specific
  вимоги на інший стек.
- Перед рішеннями щодо тестів прочитай
  [testing-policy.md](../../../ai-rules/testing-policy.md), незалежно від стека.
- Для задач конфігурації та bootstrap Java/Spring прочитай
  [infrastructure.md](../../project-init/references/infrastructure.md).
- Для задач середовищ Java/Spring backend із відповідним Docker/Properties
  стандартом прочитай
  [environments.md](../../project-init/references/environments.md).
  Не додавай цей стек або середовища до іншого проєкту через посилання.

Не копіюй ці правила в кожен task brief; передай релевантні обмеження
виконавцю так, щоб він міг їх прочитати.

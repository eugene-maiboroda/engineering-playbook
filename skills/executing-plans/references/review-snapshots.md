# Незмінні матеріали для review

Reviewer перевіряє конкретний зафіксований результат, не live working tree,
який паралельно змінюється. Не редагуй reviewed source. При виправленні
створюй наступний snapshot і передавай окремий fix diff.

## Підготовка

- Збережи root, plan/task identity, before/after state й перелік файлів.
- Для вже закоміченого результату використовуй exact BASE/HEAD commits,
  а не рухомі назви гілок або HEAD~1. Не виконуй commit автоматично.
- Для незакоміченого результату зафіксуй початковий стан задачі й окрему
  read-only для reviewer копію фактично дозволених файлів/контексту з
  manifest і content hashes. Не включай секрети, сторонні репозиторії
  або нерелевантні користувацькі зміни; не називай таку копію Git commit.
- У manifest відділи початкові користувацькі зміни від внесених задачею.
  Якщо відокремлення неможливе, уточни scope до оцінювання, не приписуй
  чужі зміни агенту.
- Додай diff із контекстом, task brief, exact report/evidence та глобальні
  обмеження. Якщо потрібні caller/context файли, захопи дозволені версії
  тієї самої основи; не змішуй live файли з reviewed snapshot.

Познач snapshot ID/hash і передай його reviewer разом зі шляхами. Read-only
інструкція агенту сама по собі не є OS sandbox; коли середовище не може
забезпечити потрібну ізоляцію, назви обмеження й не обіцяй її наявності.
Для production DevGuard потрібен окремо реалізований immutable commit
snapshot contract; ці документи не змінюють поточний QA runtime.

## Під час review

Не змінюй snapshot. Якщо він неповний, host/controller готує додатковий
контекст із тієї самої основи або новий versioned snapshot. Не дозволяй
reviewer мовчки переходити до іншого checkout/commit.

Фіксувати код можна в робочій копії після review, не в snapshot. Для
повторної перевірки вкажи попередній reviewed ID, новий ID, fix diff і
точні findings. Докази перевірок стосуються конкретного стану: не перенось
успішний результат старої версії на змінений код без релевантної перевірки.

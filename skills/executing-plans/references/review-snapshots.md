# Незмінні матеріали для review

## Спільні правила

Перевіряй конкретну зафіксовану версію результату. Не редагуй reviewed
source й не підмішуй файли з live working tree. Пов’язуй findings і докази
зі snapshot ID та перевіреною версією. Після виправлень використовуй нову
версію та окремий fix diff.

Звір root, plan/task identity, before/after state, перелік файлів, diff,
task brief, evidence та глобальні обмеження. Відділяй початкові користувацькі
зміни від внесених задачею. Якщо межі неможливо визначити, уточни scope
до оцінювання й не приписуй чужі зміни агенту. Не включай секрети,
сторонні репозиторії або нерелевантні користувацькі зміни.

## Ролі

Як основний агент або координатор, забезпеч підготовку review-пакета за
розділом поточного середовища. Підготуй матеріали сам доступними
інструментами або передай потрібні дані зовнішньому координатору.

Як reviewer, лише читай переданий пакет. Не створюй і не доповнюй
snapshot самостійно. Якщо бракує контексту, поверни точний запит стороні,
яка готує пакет; вона надає доповнення з тієї самої основи або нову версію.
Дочекайся потрібного контексту до залежного висновку. Не переходь мовчки
до іншого checkout або live файлів.

## Review із зовнішнім координатором

Якщо запуском визначено зовнішній координатор, наприклад DevGuard,
використовуй передані ним snapshot ID, шляхи, межі diff та дозволений
контекст. Підготовку, доступність та ізоляцію snapshot і запуск
погодженого reviewer залиш координатору. Не підміняй переданий snapshot.
Якщо середовище вимагає immutable commit snapshot, використовуй exact
BASE/HEAD commits; не замінюй їх копією незакомічених змін і не створюй
commit заради review.

Якщо пакет відсутній, його версію неможливо перевірити або бракує
контексту, повідом координатору, чого саме бракує і для чого. Зупини
залежну перевірку до отримання матеріалів; не заявляй неперевірену ізоляцію.

Передавай report, питання та запити на погодження через канал поточної
сесії координатора. Продовжуй дозволену роботу самостійно; не перепитуй
уже наданий дозвіл. Нове суттєве рішення поверни користувачу через цей
канал і дочекайся відповіді до залежної дії. Не запускай reviewer
самостійно, якщо запуск належить координатору, не розширюй доступ і
не вважай report дозволом на виправлення.

## Review у прямій локальній сесії Codex

Як основний агент або координатор локального review, підготуй матеріали
дозволеними локальними інструментами:

- Для вже закоміченого результату використовуй exact BASE/HEAD commits,
  а не рухомі назви гілок або HEAD~1. Не виконуй commit автоматично.
- Для незакоміченого результату зафіксуй початковий стан задачі й окрему
  read-only для reviewer копію дозволених файлів/контексту з manifest
  і content hashes. Не називай таку копію Git commit.
- У manifest відділи початкові користувацькі зміни від внесених задачею.
- Додай diff із контекстом, task brief, exact report/evidence та глобальні
  обмеження. Caller/context файли бери з тієї самої зафіксованої основи.
- Познач snapshot ID/hash і передай його reviewer разом зі шляхами лише
  в межах погодженого review.

Read-only інструкція агенту сама по собі не є OS sandbox. Якщо середовище
не забезпечує потрібну ізоляцію, назви обмеження та погодь допустимий
спосіб перевірки. Якщо контекст неповний, підготуй дозволене доповнення
з тієї самої основи або новий versioned snapshot. Питання й нові суттєві
рішення поверни користувачу в поточному чаті.

## Виправлення та повторний review

Внось лише дозволені виправлення в робочій копії після review.
Не змінюй snapshot. Для повторної перевірки вкажи попередній reviewed ID,
новий ID, fix diff і точні findings.

За зовнішньої координації передай результат виправлень через поточну
сесію й очікуй нового snapshot від координатора. Якщо потрібного commit
ще немає, повідом про це; не створюй його самостійно. Повторний review
організовує координатор у межах погодженого режиму.

У прямій локальній сесії підготуй новий snapshot за локальним розділом
і передай його для погодженого повторного review.

Зберігай докази для конкретного стану: не перенось успішний результат
старої версії на змінений код без релевантної перевірки.

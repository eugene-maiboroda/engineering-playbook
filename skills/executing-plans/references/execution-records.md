# Журнал, brief, preflight і відновлення

Спільний контракт для executing-plans та subagent-driven-development.
Обидва режими можуть використовувати ті самі матеріали при явно
погодженому перемиканні, без втрати прогресу.

## Матеріали одного плану

Обери дозволене локальне місце з урахуванням General і проєктних шляхів.
Не читай/не змінюй матеріали чужого плану. Не приймай однакове basename
файла за доказ identity: збережи canonical plan path, revision/hash і
project root. При новій версії плану зафіксуй зміну та її вплив на задачі.

Мінімум: `progress.md`, поточний exact brief, результати перевірок та
snapshot/review reports, якщо review виконується. Не створюй каталог
порожніх файлів для майбутніх задач. Це документальний workflow, не
обіцянка автоматичного SQLite Session Engine.

## Журнал

На початку: plan path/hash, root, baseline state, scope дозволеної роботи,
обраний режим. Для задач зберігай:

| Task | Статус | Залежності | Snapshot | Докази / limitations | Наступна дія |
| --- | --- | --- | --- | --- | --- |
| N | planned / in_progress / needs_context / blocked / needs_verification / complete | IDs | ID | команди й результат або report path | дія |

Рішення записуй як `Ruling: рішення — причина — наслідок помилки`, із
позначенням, чи це дрібна деталь, чи погоджене користувачем відхилення.
Суттєве рішення без approval не стає дозволеним від запису в журнал.
Окремо зберігай findings, priority, state, evidence та наступну дію.

## Brief

Збережи повний текст конкретної задачі з плану: точні значення, контракти,
обмеження, файли, критерії приймання та перевірки. Додай посилання на
специфікацію і тільки релевантні погоджені рішення попередніх задач.
Не підміняй brief коротким переказом, не дублюй у dispatch інші значення.
Якщо brief змінився, створи revision і повідом виконавця/reviewer.

## Preflight

Перед першою задачею прочитай план і специфікацію. Запиши перевірені
зв’язки: для задач зі спільним файлом або контрактом — що одна надає,
що інша використовує та чи збігається це. Для кожної задачі звір її
внутрішню узгодженість: файли, контракти, критерії й кроки.
Якщо спільних контрактів немає, запиши це, не вигадуй таблицю конфліктів.

Суттєву суперечність поверни користувачу до залежної реалізації. Не
дозволяй вимозі плану приховати дефект: якщо план суперечить специфікації
чи чинному правилу, явно покажи обидва джерела.

## Відновлення

Після restart/compaction спочатку перевір identity журналу, поточний
план/hash і фактичні артефакти. Зістав completion із доказами та станом
коду; запис complete не є доказом, якщо snapshot не відповідає поточній
роботі. Завершене не виконуй повторно. Для незавершеного fix loop прочитай
останній report і продовжуй із записаного раунду, не скидай ліміт.

Не видаляй невідомий журнал і не присвоюй його іншому плану. Якщо evidence
втрачені, чесно познач невідомість та погодь потрібну повторну перевірку.
Git history допомагає лише для реально створених користувачем commits;
незакомічені результати відновлюються зі збережених матеріалів, а не з
вигаданих SHA. Втрата workspace не виправдовує автоматичне повторення
потенційно небезпечних операцій.

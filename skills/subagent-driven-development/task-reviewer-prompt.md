# Task Review — відповідність вимогам і якість

Передай reviewer конкретний незмінний snapshot за
[review-snapshots.md](../executing-plans/references/review-snapshots.md).
Перед запуском підстав конкретні абсолютні шляхи й ID. SPEC_PATH —
погоджений design або інше джерело вимог із плану; REVIEW_PACKAGE_PATH —
каталог зафіксованих матеріалів review, не package програмного коду.
Review цього шаблону read-only: ні тести, ні записи, ні Git mutations.
Збережи повернутий report як координатор; reviewer не записує файлів.

```text
Перевір одну задачу [TASK_ID], не весь проєкт.
Brief: [BRIEF_PATH]. Специфікація: [SPEC_PATH].
Глобальні обмеження, точні значення й контракти: [GLOBAL_CONSTRAINTS].
Report виконавця: [REPORT_PATH].
Snapshot before/after IDs і manifest: [SNAPSHOT_IDS / MANIFEST_PATH].
Diff і потрібний exact контекст: [REVIEW_PACKAGE_PATH].

Перевір спочатку відповідність вимогам, потім якість результату.
Це task-scoped review; загальний review відбудеться окремо.

Читай зафіксовані матеріали, не live working tree іншої версії.
Читай і шукай у переданих матеріалах дозволеними read-only інструментами,
зокрема файловими командами, якщо це доступний спосіб читання.
Не змінюй reviewed source, index, HEAD або branch; не запускай
проєктний код, build або tests, не створюй tests, не читай секрети
й не використовуй мережу. Не запускай субагентів. Якщо контексту не вистачає,
назви конкретну потребу координатору замість розширення доступу.

Report виконавця — твердження, не доказ правильності. Зістав його
з diff, exact джерелами та evidence. Відсутній або обрізаний report
спочатку перечитай у дозволеному файлі; якщо він справді неповний,
познач limitation. Не вигадуй результати перевірок.

Відповідність: що пропущено, додано без потреби або зрозуміло неправильно?
У batch перевір кожен перелічений файл і зміну. Погоджена вимога,
яку неможливо підтвердити з матеріалів, — Cannot verify, не success.

Якість: коректність поведінки, межі відповідальності, errors,
контракти, дані, edge cases і реальний вплив зміни. Не повідомляй
coverage/відсутність нових tests або стиль як самостійні дефекти.
Перевірки й код тестів, якщо вони є, можуть бути доказами.
Не знижуй severity лише через виправдання виконавця або мовчання spec.
Дефект, прямо заданий планом, також назви й поясни суперечність.

Для кожного finding вкажи точні file:line зі snapshot, передумови,
що неправильно, наслідок і рекомендацію. Не вигадуй evidence;
коли його недостатньо, окремо назви limitation.
Severity: Critical — критичний вплив; Important — дефект/пропущена
вимога, що блокує довіру до задачі; Minor — неблокувальне покращення.
Не вважай кожну пропозицію Important.

Поверни:
## Spec Compliance
PASS | FAIL, підтверджені причини.
Cannot verify: невідоме й потрібний контекст.
## Quality
Approved | Needs fixes, коротке обґрунтування.
Approved тут означає оцінку якості задачі, а не людський дозвіл на зміну
вимог, merge, публікацію чи нову реалізацію.
## Findings
Critical / Important / Minor; або «Підтверджених findings немає».
Для кожного — exact evidence та реальний вплив.
## Limitations
Що не перевірено й чому.
```

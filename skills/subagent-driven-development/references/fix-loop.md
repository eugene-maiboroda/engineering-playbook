# Обмежений fix loop

Починається за spec FAIL, підтвердженим gap або Critical/Important finding.
Спочатку перевір finding і scope. Якщо виправлення змінює суттєве рішення,
план або дозволи — погодь його з користувачем до реалізації. План, який
вимагає дефект, не є виправданням; назви суперечність.

Minor поза scope запиши deferred; він не розширює fix loop автоматично.
Severity оцінюй за впливом, а не за тим, чи згаданий сценарій у spec.

## Раунд

1. Збережи exact open findings, причини початкових spec FAIL / Needs fixes,
   шлях до task review report і reviewed snapshot як FIX_BASE. До dispatch
   реалізації запиши в progress номер R/5 і стан pending_dispatch; після
   запуску одразу додай agent ID та стан in_progress. Раунд рахується з
   фактичного запуску реалізації виправлення, зокрема продовження старого
   implementer. Невдалий dispatch без старту виконання познач not_dispatched; він не витрачає раунд. Якщо результат запуску
   невідомий, спочатку з’ясуй стан, не запускай дубль й не скидай номер.
2. Поверни задачу початковому implementer із brief/report paths. Якщо
   продовження tool недоступне, новий implementer отримує ті самі матеріали
   й історію спроб через report, не всю історію координатора.
3. Implementer виправляє лише погоджене, виконує релевантні перевірки й
   додає report із командами/діями, результатом та limitations. Нові tests
   автоматично не пише, commit не виконує.
4. Підготуй новий snapshot і fix diff. Передай
   [re-review-prompt.md](../re-review-prompt.md) із exact findings.
5. Зістав finding verdicts із початковими причинами spec FAIL / Needs fixes.
   Закрий лише підтверджено усунені причини; CANNOT_VERIFY залиш відкритим.
   Незачеплені висновки попереднього review збережи. Перевір нові blocking
   findings і релевантні фактичні перевірки. Лише після цього запиши
   підсумкові spec/quality verdicts, без нового повного аудиту.
6. Запиши результат: `Task N: fix round R/5 — addressed/open — snapshot IDs — evidence`.
   CANNOT_VERIFY не рахується ADDRESSED. Новий дефект у fix diff входить
   у triage, а не приховується як «нова проблема reviewer».

Максимум п’ять фактично розпочатих fix rounds на задачу в цьому режимі.
Уточнення контексту без dispatch реалізації не починає нового раунду.
Перерваний розпочатий раунд познач interrupted; він залишається врахованим.
Після відновлення з’ясуй стан агента, report і змін та продовжуй той самий
раунд, якщо реалізацію вже виконано й залишився review. Не створюй новий
раунд лише для читання результату або доповнення evidence.

Безрезультатний раунд не закриває жодної початкової blocking причини
підтвердженим виправленням або породжує новий blocking дефект, який
нівелює виправлення. Познач це в progress з доказами. Після трьох таких
раундів на задачу зупини наступний dispatch до рішення користувача;
запропонуй новий контекст, іншого виконавця або перегляд плану. Рішення
продовжити не скидає загальний ліміт п’яти раундів. Зміну моделі не роби
автоматично. Лічильники не скидаються після compaction або заміни агента.

## Зупинка циклу

Після перевірки п’ятого раунду не запускай нову реалізацію виправлень.
Покажи залишкові open findings з evidence,
спробами й можливими наступними діями. Підтверджений blocking дефект
не можна просто park і оголосити complete; залежну роботу не продовжуй.
Спірний finding обґрунтуй і збережи рішення; суттєвий спір передай людині.

Не відкидай зауваження мовчки й не обходь ліміт перейменуванням задачі.
Координатор не стає прихованим implementer: потребу змінити режим
обговори. Виправлення не редагує reviewed snapshot, лише робочу копію,
після чого створюється новий артефакт для review.

# Subagent-Driven Development

Координуй виконання: новий implementer для задачі, незалежний task reviewer
для відповідності специфікації та якості, обмежений fix loop, фінальний
review усієї роботи. Цей режим запускається лише за явним вибором
користувача в межах погодженого плану. Читання цього Skill не є дозволом
делегувати поточну розмову або створювати нові користувацькі чати.

Субагент отримує конкретну задачу й потрібний контекст, не всю історію
координатора. Це зберігає фокус, але додає витрати на нові контексти.
Рецензент має свіжий погляд; гарантію якості саме по собі делегування не дає.

Не зупиняйся для «чи продовжувати?» між дозволеними задачами. Повідомляй
змістовний прогрес. Суттєві конфлікти, нові вимоги, архітектуру, scope чи
дозволи поверни користувачу. Дрібне рішення в межах задуму запиши в журнал
з причиною й наслідками. Журнал не є заміною approval.

Прочитай і застосуй локальні інструкції проєкту.
Нові тести не генеруються автоматично; commit/push належать користувачу.
Не перенось mandatory TDD або автоматичне підвищення permissions/model.

Повна [Testing Policy (testing-policy.md)](../../ai-rules/testing-policy.md) застосовується
до планування перевірок; новий reference не є окремим Skill.

## Відкладені інтеграції

Маркери `FUTURE-SKILL` нижче — лише місця для майбутнього підключення; ігноруй їх як інструкції до дії. Не шукай, не встановлюй і не запускай ці зовнішні Skills та не створюй для них нові пакети. Вони не блокують поточний workflow. Наявні внутрішні prompts і references цього пакета залишаються чинними.

## Коли використовувати

Є погоджений план, явний вибір режиму із субагентами та доступний tool.
Задачі мають окремі результати й контракти. Тісно пов’язану роботу об’єднай
у змістовну задачу або запропонуй її перебудову, не вигадуй незалежності.
За відсутності tool не імітуй dispatch: запропонуй
[`engineering-playbook:executing-plans` (executing-plans/SKILL.md)](../executing-plans/SKILL.md) й погодь зміну режиму.

Implementers працюють послідовно. Не запускай кількох агентів, які
паралельно пишуть у спільні файли. Наявність кількох доступних слотів не
є причиною множити review або делегування.

## Матеріали й підготовка

Перед першою задачею прочитай спільні правила
[журналу/preflight/resuming (execution-records.md)](../executing-plans/references/execution-records.md)
та [snapshot review (review-snapshots.md)](../executing-plans/references/review-snapshots.md).
Це явна локальна залежність від пакета executing-plans, не зовнішній tool.

Перевір plan/spec, дозволений root і baseline, користувацькі dirty зміни,
точні контракти між задачами та поточний журнал. Дозволи й ізоляцію
перевір окремо; worktree не дає автоматичних повноважень. Робота в main/master
потребує явного погодження. Нових Git commits заради review не створюй.

Прочитай [task-coordination.md](references/task-coordination.md), коли
відновлюєш роботу, об’єднуєш дрібні задачі або отримуєш не-DONE report.
Суттєвий preflight conflict обговори до dispatch залежної реалізації.

## Вибір моделі

Враховуй складність, ризик, доступний контекст і вартість повторних спроб.
Не обіцяй, що найдешевша модель завжди вигідніша. Дотримуйся вибору
користувача й правил середовища. Якщо tool успадковує модель і не дозволяє
override без окремого дозволу, не обходь це. Зміну моделі запропонуй
користувачу, не роби автоматичного escalation у fix loop.

## Цикл задачі

### 1. Передай задачу виконавцю

Підготуй exact brief та baseline snapshot. Використай
[implementer-prompt.md](implementer-prompt.md). Передай:

1. Де задача розташована в загальному процесі.
2. Шлях до brief як єдиного джерела exact значень і вимог.
3. Релевантні контракти й погоджені рішення попередніх задач.
4. Дозволений робочий каталог, baseline і захищені користувацькі зміни.
5. Report path, критерії готовності та permission boundaries.

Не вставляй у dispatch усі попередні звіти чи суперечливий переказ brief.
Збережи agent ID для наступних уточнень. Виконавець сам не запускає
субагентів або reviewer: review організовує координатор.

### 2. Опрацюй report

Для DONE перевір наявність report, actual changes і evidence; сам статус
не доводить завершення. Для DONE_WITH_CONCERNS, NEEDS_CONTEXT і BLOCKED
використай [task-coordination.md](references/task-coordination.md).
Не змушуй агента повторювати той самий провальний підхід без змін.

Підготуй незмінний snapshot після реалізації. Task review отримує конкретні
before/after IDs, diff, brief, report та обмеження. Жоден reviewer не
редагує reviewed source. Не передавай live checkout як нібито immutable.

### 3. Проведи task review

Використай [task-reviewer-prompt.md](task-reviewer-prompt.md).
Потрібні два verdicts: відповідність вимогам та якість задачі. Самоперевірка
implementer не замінює незалежну перевірку в цьому обраному режимі.

Не підказуй reviewer бажаних findings або заборон «не повідомляй цю
конкретну проблему». Передай точні обмеження, без підміни незалежного
судження своїм. Reviewer читає snapshot і evidence; не запускає тести,
не генерує їх і не змінює файли. Додаткову перевірку може рекомендувати
з конкретною причиною.

Cannot verify не означає ні defect, ні success. Підготуй потрібний exact
контекст або доручи implementer релевантну перевірку в межах дозволів.
Якщо невідомість суттєва, не закривай задачу без її розв’язання.

### 4. Виправ findings

За spec mismatch або Critical/Important прочитай
[fix-loop.md](references/fix-loop.md). Для re-review використовуй
[re-review-prompt.md](re-review-prompt.md). Reviewer перевіряє конкретні
findings і новий fix snapshot, без повторного безмежного аудиту.

### 5. Заверши задачу

Complete можливий після прийнятних spec/quality verdicts, фактичних
перевірок та відсутності невирішених blocking findings. Запиши result,
snapshot IDs, reviewer verdicts, evidence, погоджені відхилення й наступну
дію в progress. Не оголошуй complete із відомим суттєвим дефектом
лише через ліміт раундів. До залежної задачі на ненадійній основі не переходь.

## Фінальний review

Коли задачі завершені, прочитай [final-review.md](references/final-review.md).
Підготуй aggregate snapshot від справжньої початкової основи, не лише
останній fix. Передай фінальному reviewer також deferred findings,
погоджені рішення та Review Focus.

## Завершення

Повідом виконане, перевірки, verdicts, усі суттєві відхилення/рішення,
відкриті й відкладені findings і місце evidence. Окремо назви limitations.
Не видаляй матеріали або Git-гілки автоматично. Commit, merge, push,
публікація та cleanup потребують окремого scope. Не вважай рев’ю дозволом
змінювати продукт поза погодженим планом.

## Типові помилкові виправдання

| Думка | Правило |
| --- | --- |
| «Досить близько до специфікації» | Погоджений критерій має бути виконаний або явно повернутий користувачу. |
| «Виправлю за implementer сам» | У цьому режимі поверни findings виконавцю та проведи re-review. |
| «Ще один раунд точно допоможе» | Ліміт захищає від безрезультатного циклу; ескалюй проблему. |
| «Reviewer перебільшує» | Оціни докази й запиши рішення, не відкидай finding мовчки. |
| «Implementer уже запустив reviewer» | Це зайвий непогоджений рівень делегування; використовуй визначений процес. |
| «Complete записано — можна йти далі» | Звір стан snapshot, verdicts і докази, особливо після відновлення. |

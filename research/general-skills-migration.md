### Ідея розвитку Project-init — ще не реалізація

Користувач запропонував надалі створювати початковий Java/Spring проєкт
агентом із однієї команди або декларативного JSON: ідентичність проєкту,
цільова папка, версія Java, версія Spring Boot, build tool і вибрані
capabilities/dependencies (наприклад, validation або security). Dropdown UI
в DevGuard — можлива пізніша оболонка того самого контракту, не перший
обов’язковий крок і не нова IDE.

Потрібно окремо погодити:

1. Контракт входу, обов’язкові поля та дозволені defaults без зайвих dependencies.
2. Правила перевірки сумісності версій і спосіб актуалізації джерел. Конкретні версії та матрицю сумісності зараз не визначено; перед реалізацією перевіряти офіційні актуальні джерела, не дозволяти довільну комбінацію лише через валідний JSON.
3. Попередній показ того, що буде створено, межі запису й відмову від мовчазного overwrite наявного проєкту.
4. Результат генерації, перевірку фактичних файлів/build та межу між skeleton і подальшою foundation implementation.
5. Чітке розділення нового проєкту й наявного: генерація skeleton не є обов’язковою частиною Brainstorm фічі.

**Це запропоноване розширення попередньої концепції:** чинний General і
раніше погоджений Project-init передбачають ручне створення skeleton
користувачем та перевірку агентом. Нова ідея додає кероване створення
агентом. До окремого погодження не змінювати старе правило й не запускати
генератор. Project-init не замінює Writing Plans; його точну роль і
порядок визначимо при проєктуванні цієї можливості.

## Погоджені рішення, які не слід втратити

- Brainstorm незалежний від DevGuard, працює українською й зараз лише текстом.
- Пропорційність: погоджений fix або задача чинного плану не потребують нового повного Brainstorm.
- Після погодження дизайну — Writing Plans. Не відновлювати ранню помилкову заміну цього переходу на Project-init.
- Суттєві рішення щодо потреб, поведінки, вигляду або принципів результату погоджуються; дрібні деталі можуть залишатися виконавцю.
- Spike/PoC — окремий погоджений ізольований експеримент із поверненням висновків у Brainstorm.
- Design readiness — обов’язкова самоперевірка; Builder Check — незалежний review за рішенням користувача, а не другий автоматичний агент.
- Користувач створює skeleton; Project-init перевіряє фактичний стан, не переобирає архітектуру. Foundation implementation — перша погоджена задача після Planning.
- Нові tests, обов’язковий TDD, автоматичні commit/push не додаються. Покращення правил і підходів можна обґрунтовано пропонувати, не застосовуючи суттєве відхилення мовчки.
- Приклади програмного коду — Java; реальний план відповідає поточному проєкту. Непрограмним задачам не нав’язуються кодові файли й сигнатури.
- Execution-пакети не запускаються лише через їх читання. Додаткові агенти — у межах явно обраного користувачем режиму.
- Створені внутрішні reviewer prompts збережені. Окремий DevGuard цикл user commit → QA → selected findings → ручний developer handoff ними не підміняється.

## Перевірки: що вони підтверджують

Для створених пакетів перевірено YAML frontmatter, name/description,
локальні посилання, anchors де вони є, code fences та відповідність
погодженим рішенням. В execution Skills є рівно по п’ять неактивних
маркерів FUTURE-SKILL. Створені prompts і references збережені.

Це структурна й ручна перевірка документів, не незалежний поведінковий
eval. Агентів для тестового виконання планів не запускали, глобальну
інсталяцію/discovery не перевіряли, runtime DevGuard не змінювали.

успіх не заявляється. YAML перевірено Ruby YAML parser без інсталяції
нових залежностей. Жодних commit/push не виконано.

Поточна бібліотека не розширюється цими пакетами. Не шукати, не
встановлювати й не запускати їх за маркером. Маркер — нотатка редактору,
не вимога виконання й не причина блокувати поточний процес.

| Відкладена робота | Місце майбутнього підключення | Що є зараз |
| --- | --- | --- |
| using-git-worktrees | Підготовка обох execution Skills | `FUTURE-SKILL: using-git-worktrees`; немає зовнішньої залежності чи auto worktree workflow |
| systematic-debugging | Виконання кроків / виправлення findings | `FUTURE-SKILL: systematic-debugging`; наявні правила дослідження причин діють без нового пакета |
| verification-before-completion | Завершення задачі | `FUTURE-SKILL: verification-before-completion`; evidence залишається обов’язковим, окремий пакет не потрібен зараз |
| requesting-code-review | Фінальна перевірка | `FUTURE-SKILL: requesting-code-review`; не додаємо зовнішній пакет, вже створені локальні review prompts збережено |
| finishing-a-development-branch | Завершення execution | `FUTURE-SKILL: finishing-a-development-branch`; Git mutations і cleanup не автоматизуються |
| Visual Companion / Visual Component | Майбутнє доповнення Brainstorm/DevGuard | Ідея в roadmap DevGuard; зараз лише текст, без серверів або visual MD |
| writing-skills | Методика розвитку самих Skills | Відкладено користувачем; окремий пакет не створюємо |

Маркери перших п’яти робіт розташовані в обох основних execution SKILL.md.
Знайти їх: `rg -n 'FUTURE-SKILL:' skills/`. Відкладення не прибирає
наявних внутрішніх інструкцій. Ця таблиця — актуальний реєстр відкладених робіт.
Повернення до будь-якої роботи з цієї таблиці — лише за новим рішенням
користувача, не наслідок завершення поточного milestone.


## Погоджена модель DevGuard / Codex / Engineering Playbook

Зафіксовано 2026-10-27 після уточнення користувачем. Це рішення про
майбутню інтеграцію, не твердження про її готову реалізацію й не дозвіл
почати продуктовий backend. Поточний QA runner не змінюється автоматично.

### Відповідальність і сесії

- Користувач — центр прийняття рішень. DevGuard — пульт керованих
  інженерних процесів: запуск, пауза/зупинка, налаштування, результати,
  погодження та майбутній контроль доступів. Це не дзеркало всіх чатів Codex.
- Codex Desktop залишається окремим інструментом вільної роботи над тим
  самим проєктом. Виконання підготовленого в DevGuard плану можна почати
  там, передавши файл плану, без історії чату DevGuard.
- Для інтерактивних процесів DevGuard обрано локальний Codex app-server.
  DevGuard зберігає зв’язок своєї сесії з конкретним Codex thread ID.
  Кожна відповідь користувача — наступний turn того самого thread;
  читання reference або нового Skill саме по собі не створює інший чат.
- При обриві зв’язку відновлюємо збережений thread через thread/resume,
  а не починаємо новий автоматично. Зберігання ID, подій, обробка помилок
  і відновлення — майбутній контракт runner. Якщо історія недоступна,
  явно відновлюємо контекст зі збережених матеріалів; не заявляємо повну
  пам’ять. Довга розмова має обмежений контекст і може стискатися.
- Початок Brainstorm у DevGuard — явна дія користувача, наприклад кнопка.
  Вибраний сценарій має пріоритет; за його відсутності агент визначає його
  з запиту й фактичних матеріалів. Репозиторій може бути лише skeleton.

### Самоперевірка та незалежний reviewer

Readiness виконує основний агент у тому самому thread. Незалежний
Builder Check отримує новий thread без історії основного діалогу:
завдання reviewer, конкретну незмінну версію дизайну (або плану для
відповідного виду review), потрібні обмеження й джерела. Він оцінює
переданий документ як сторонній виконавець. Для Builder Check не потрібно
копіювати всю розмову або автоматично досліджувати весь проєкт; потрібний
контекст має бути в документі й явно наданих матеріалах. Відсутній контекст
reviewer позначає питанням, а не вигадує. Це не універсальна заборона
контексту для code review: його потреби визначає конкретне завдання.

DevGuard пов’язує reviewer із основною роботою, зберігає report і повертає
його в основний thread наступним turn. Основний агент закриває питання,
відповіді на які вже є в розмові, й уточнює нові суттєві рішення з
користувачем. Reviewer не змінює reviewed source і не затверджує результат.

Увімкнене користувачем налаштування «запускати review» є попереднім дозволом
на відповідний review у заданих межах; повторне питання не потрібне.
Автоматизація перевірки не є автоматичним approval дизайну/плану й не
розширює права читання, запису чи запуску інших агентів.

### Доступ до локальної бази

Engineering Playbook — звичайний репозиторій Skills і правил, не plugin.
Створений у цьому обговоренні plugin видалено, marketplace відключено,
маніфест і каталог пакування прибрано. Namespace engineering-playbook:skill
залишається умовним іменем із обов’язковим посиланням на відповідний файл;
це не команда зареєстрованого plugin.

На початку thread DevGuard має передати абсолютні project root і Playbook
root та початковий Skill і забезпечити дозволені інструменти читання.
Корені також зберігаються в локальному AGENTS.md за правилами General.
Codex сам читає потрібні Skills, AI rules і references: Markdown links
розв’язуються від файла-джерела, шляхи від кореня Playbook — від переданого
кореня. DevGuard не пересилає кожний reference окремим запуском. Питання
потрібне лише при невідомому шляху, недоступному файлі чи браку дозволу.
GitHub identity не замінює локальний шлях. Наявний QA із вимкненими
інструментами не набуває цих можливостей від зміни Markdown.

### Спільні документи між інструментами

- Design і plan окремі для фічі: дата + реальна назва теми. Нова фіча
  створює нові документи, уточнення тієї самої — оновлює чинні; збіг назви
  не дозволяє мовчазний overwrite. Поточний формат має дату без часу.
- План передає виконавцю design, потрібні правила Playbook, точні шляхи
  й критерії перевірки. Не покладається на історію DevGuard або пам’ять
  користувача; не копіює весь Playbook чи повну реалізацію без потреби.
  Повноту цього handoff ще перевірити в найближчому review.
- Один спільний docs/progress.md на проєкт (наявний погоджений шлях має
  перевагу): усі фічі, інструменти й чати. Читати перед роботою, оновлювати
  після кожної задачі або зміни до наступної. Писати для іншого чату:
  що/навіщо змінено, перевірки, рішення, незавершене й наступний крок.
- AGENTS.md зберігає короткі постійні інструкції та точні посилання.
  Спільні файли синхронізують результати, не історії чатів. Паралельний
  запис і перевірка фактичного стану потребують окремого узгодження;
  Markdown сам не забезпечує блокування чи автоматичну синхронізацію.

### Review стилю нових references

За зауваженням користувача прибрано повторну маршрутизацію з
project-agent-instructions: checkpoint і умови входу залишаються в General.
Reference тепер містить налаштування, перевірку й повернення до Skill.
Скорочено повтори шаблона/політик, пояснення механіки Codex і історії
міграції. З implementation-rules прибрано вступ про його походження,
з project-initialization — історичні пояснення й повторний підсумок.
Project-progress залишає конкретні операції журналу; Testing Policy
не змінено. Аудит збереження General є звітом для review, не виконуваною
інструкцією: джерело, карта й межі перевірок у ньому збережені.

Пояснення інтеграції залишаються в цьому плані: AGENTS.md завантажується
Codex на старті run/сесії, не гарантує перечитування на кожне повідомлення;
посилання не завантажують цільові файли автоматично. Установник та
інтерактивний runner DevGuard ще не реалізовані. Це не кроки налаштування
AGENTS.md і тому прибрані з операційного reference.

### Уточнення стилю General під час review

З General прибрано пояснення про автоматичне завантаження, відсутній
установник/валідатор і стан інтеграції. Залишено дії: checkpoint, умовний
перехід до налаштування, повернення до Skill, застосування правил і
роботу з документами. Метадані стану реалізації зберігаються в research.
За уточненням користувача поточні Skills є зразком і в цьому проході
не редагуються; подальше редагування інших технічних AI rules — окремо.

### Уточнення входу Brainstorm: перевірка до General

За прямим уточненням користувача Brainstorm спочатку перевіряє блок
AGENTS.md і лише за неповнотою, зміною правил/підключення або суперечністю
читає General. Повне актуальне налаштування дозволяє пропустити General
та project-agent-instructions. У шаблон і checkpoint додано Scope policy
та Access policy, щоб цей перехід не втрачав спільних меж General.
Змінено лише вхід Brainstorm і відповідні поля налаштування; основний
процес обговорення не змінювався. Це замінює попередній обов’язковий
маршрут Brainstorm → General на кожному новому thread.

## Видалення General і повторна перевірка references

General видалено за прямим дорученням користувача. Brainstorm перевіряє
AGENTS.md і при прогалині переходить прямо до project-agent-instructions.
Інші Skills використовують локальні інструкції та конкретні policies;
історичні згадки General нижче/вище є описом джерела міграції.

Результат звірки трьох references:

- Project Progress зберігає окремий контракт журналу між чатами: зміст
  запису, актуальний стан + історія, докази, паралельні правки й перенесення
  старих журналів. Skills задають момент оновлення, не повторюють контракт.
- Project Agent Instructions зберігає процедуру створення AGENTS.md,
  шаблон полів, правила абсолютних/відносних шляхів і перевірку результату.
  Brainstorm перевіряє готовність, цей reference виправляє прогалини.
- Project Initialization частково повторює Brainstorm/new-project. Окремо
  потрібні ручне створення skeleton, повний checklist його перевірки та
  перелік foundation. Дубль контексту/обговорення прибрано, збережено
  його приклади й вимоги в new-project. Нового Project-init Skill немає.

### Review Project Initialization: межа відповідальності

Прибрано визначення переходу до Writing Plans із reference ініціалізації.
Він повертає результати перевірки skeleton до поточного кроку викликового
Skill. Склад foundation перенесено у Writing Plans без втрати переліку
й посилань на infrastructure/environments. Переходом після дизайну керує
Brainstorm; reference перевірки не запускає наступний процес.

### Project Init: єдине розташування технічних стандартів

За дорученням користувача infrastructure, environments, web-api,
error-handling і project-conventions видалено з ai-rules після перевірки
відповідності копій. Чинні джерела — skills/project-init/references/.
Вхідні файлові посилання оновлено; ці references можна застосовувати
окремо до наявного проєкту без створення skeleton. Project-init залишається
draft; точний POM, базові dependencies та JSON ще не погоджені.

### Project Init: два погоджені сценарії

Користувач погодив create (явно довірене агенту створення) та inspect
(підключений вручну створений проєкт, перевірка й рекомендації без
регенерації). Режим передається JSON або явним запитом; майбутня галочка
Create Project — можливий UI, не реалізований у DevGuard цим проходом.
Оновлено Project Init, input-contract, старий checklist і входи з
Brainstorm/Writing Plans. Унікальні налаштування наявного проєкту
зберігаються; defaults не застосовуються до них автоматично.
